# Проверка копания Minecraft 26.1

Проверено 14 ноября 2026 по именованным классам локального `client.jar` Minecraft 26.1 через `javap -p -c`. Это анализ исполняемого кода Mojang, а не предположение по поведению Mineflayer. Официальная страница версии: https://www.minecraft.net/en-us/article/minecraft-java-edition-26-1.

SHA-256 проверенного JAR: `bc6194c61566b587f196090d730698f2191170f7580adb143e4ff839939d3840`.

Локальные дизассемблированные классы находятся в игнорируемом `data/research/`; исходный код Mojang в репозиторий не включён.

## Зачарования и скорость

`Enchantments.bootstrap` задаёт для Efficiency модификатор `MINING_EFFICIENCY`, операция `ADD_VALUE`, слот `MAINHAND`, величина `LevelsSquared(1)`. `LevelBasedValue.LevelsSquared.calculate` считает квадрат уровня плюс добавку. Для Efficiency V это 26, а не «уровень зачарования 26».

`ItemStack.getDestroySpeed` обращается к компоненту `Tool`. `Tool.getMiningSpeed` выбирает первое подходящее правило со скоростью. У обычного незеритового материала скорость подходящего инструмента равна 9 (`ToolMaterial.NETHERITE`). Компонент `tool`, присланный сервером, может изменить эту скорость.

`Player.getDestroySpeed` прибавляет `MINING_EFFICIENCY`, только если исходная скорость инструмента больше 1. Затем применяются Haste/Conduit, Mining Fatigue, `BLOCK_BREAK_SPEED`, погружение глаз и штраф за отсутствие опоры. `BlockBehaviour.getDestroyProgress` делит скорость на твёрдость и на 30 либо 100 в зависимости от правильности инструмента для добычи.

В просмотренной записи Shard Axe: Efficiency V, Silk Touch I, Unbreaking III, Mending I; атрибут эффективности +26; переопределения компонента `tool` нет. При стоянии на земле для елового бревна:

```
скорость = 9 + 26 = 35
прогресс за тик = float(float(35 / 2) / 30) = 0.5833333134651184
два прибавления прогресса достигают 1
```

Расчёт Botify для этой записи соответствует клиенту. Описание предмета «Breaks Trees Instantly» не является основанием объявить блок мгновенно разрушаемым на клиенте. Эффект срубания дерева отсутствует в переданном списке зачарований; его реализация на сервере неизвестна.

## Порядок действий клиента

`MultiPlayerGameMode.startDestroyBlock` отправляет START с prediction sequence. Для немгновенного разрушения `continueDestroyBlock` прибавляет прогресс на клиентских тиках. При достижении 1 он отправляет STOP, локально предсказывает разрушение, сбрасывает прогресс и устанавливает `destroyDelay = 5`.

`Minecraft.continueAttack` вызывает продолжение копания и взмах при удержании кнопки. Пять тиков — задержка перед следующим разрушением, а не пять секунд ожидания ответа сервера. START и STOP не посылаются заново на каждом взмахе.

`BlockStatePredictionHandler.updateKnownServerState` сохраняет серверные изменения блока, а `endPredictionsUpTo` при ACK сверяет предсказание с сохранённым состоянием. ACK подтверждает обработку последовательности; сам по себе он не означает, что блок разрушен. При восстановленном блоке и продолжающемся удержании клиент может продолжить копание после задержки.

Важная тонкость: `sameDestroyTarget` не проверяет флаг `isDestroying`. Если позиция и компоненты предмета сохранились, `continueDestroyBlock` может продолжить накопление прогресса и отправить следующий STOP без нового START. При смене цели/компонентов выбирается `startDestroyBlock`. Поэтому формулировка «обычный клиент всегда повторяет START/STOP» была бы неверной. Botify пока сохраняет полные отдельные попытки START/STOP; исправление задержки не является полной копией машины состояний vanilla.

`sameDestroyTarget` сравнивает позицию и `ItemStack.isSameItemSameComponents`. Botify пока проверяет тип инструмента, а обёртка удержания дополнительно проверяет слот между попытками; полной эквивалентности vanilla для изменения компонентов в середине копания нет. Это отдельное ограничение, не установленная причина наблюдаемого отказа: в последней неудачной записи до STOP нет события смены предмета.

Vanilla `ServerPlayerGameMode` использует серверное время начала и прогресс; при недостаточном прогрессе STOP может запустить отложенное разрушение. Поэтому один повторный пакет с прежним блоком без ACK соответствующего STOP не служит достаточным основанием для немедленного перезапуска.

## Что показали записи и что изменено

Последняя просмотренная неудачная попытка: START sequence 13, STOP sequence 14 через 100 мс, прежнее бревно и ACK 14 через 177 мс. Botify продолжал взмахи, но ждал таймаут до 5101 мс. Следующая попытка: START 15, STOP 16 через 101 мс, воздух через 251 мс. Скорость и перечисленные зачарования одинаковые.

Исправлена обработка уже разрешённого сервером предсказания в `src/held-dig.js`: после возврата прежнего блока **и** ACK текущего STOP новая попытка разрешается, когда прошли пять клиентских тиков после STOP. Между таким STOP и следующим START не добавляется ABORT. При отсутствии достаточного ответа остаётся прежний таймаут; ACK начала, старый ACK или один ACK без обновления блока не ускоряют повтор.

Общий мир бота остаётся серверным: локальное предсказание воздуха не используется как подтверждение успеха. Это намеренное отличие от визуального клиента.

Причина отказа первой попытки на DonutSMP этим анализом не установлена. Проверки локального протокольного сервера подтверждают обработку возврата/ACK и интервалы пакетов; они не воспроизводят закрытые плагины или форк античита DonutSMP.
